# 08 — Web app spec

Localhost first. Vercel later, with no code changes required.

## What it is

A recruiter-facing UI over the pipeline output. Not a dashboard for its own sake — its job is to make
the two claims in the design doc **touchable**:

1. *"The scoring is transparent, not a black box"* → the user can see every sub-score and re-weight
   the model live.
2. *"The system tells you who to call and who can introduce you"* → the intro path is the most
   prominent thing on a candidate card.

## Architecture — where the scoring runs

**Python computes the sub-scores. The browser does only the weighted sum.**

This matters. Sub-scores (`required_skills: 0.8`, `role_family: 1.0`, `seniority: 1.0`, …) are
**weight-independent** — they describe the candidate, not the model configuration. So:

- the Python pipeline stays the single source of truth for all matching logic
- the browser recombines pre-computed components with whatever weights the sliders are set to
- sliders re-rank instantly with **zero duplicated logic and zero drift risk**
- the site is fully static — no backend, no API routes, no runtime dependency, deploys anywhere

```
run.py  ──►  output/JOB001_shortlist.csv        (the graded deliverable)
        └─►  web/public/data/pool.json          (the app's data contract)

browser:  fit = Σ (component[i] × weight[i]) / Σ weight[i] × 100
```

**Invariant to test:** with default weights, the browser's computed score must equal the Python
score to 1dp. Ship the Python-computed defaults inside the JSON so a mismatch is detectable, and
assert it in a test.

## Stack

- **Next.js (App Router) + TypeScript + Tailwind**, static export (`output: 'export'`)
- No database, no auth, no API routes for v1
- `npm run dev` for localhost; `vercel deploy` later with no changes
- Data loaded from `web/public/data/pool.json`, regenerated by `python run.py --emit-json`

## Screens

### 1. Shortlist (default view)
- Job selector across the 4 open roles
- Candidates grouped by priority tier: **Call this week** / **Direct outreach** / **Nurture**
- Card per candidate: name, title @ company, location, years
  - two small bars — **fit and signal** — with the numbers
  - matched required skills as chips (✓ has it, ~ family match, ✗ missing)
  - **intro path called out**: "Maya Levi (Sr ML Engineer) — overlapped at Mobileye 2019–21"
  - the recruiter note from the badge scan, if present
  - `above_band` / `low confidence` flags where they apply
- Sort and filter: by fit, by signal, by conference, by role family

### 2. Weight tuner (the money feature)
A side panel with a slider per component — five for fit, eight for signal — plus the tier
thresholds. Everything re-ranks live as they drag. Include:
- a **Reset to defaults** button
- a **"what changed"** indicator: which candidates moved into or out of the top 10
- a one-line explanation under each slider of what that component measures

This is the feature that proves the transparency claim. Let them break the model and watch it
respond — that is far more convincing than a paragraph saying it is explainable.

### 3. Candidate detail
- Full fit breakdown as a horizontal bar chart, component by component, showing
  `earned / available` for each
- Signal breakdown the same way (8 components)
- All warm paths listed, not just the best one
- Full profile: skills, past titles with dates, past companies, industry
- Conference context and days since contact
- The **pre-written outreach draft** (see `docs/09-mock-integrations.md`) with a copy button
- The gate decision and its three signals, so admission is auditable per person

### 4. Talent pool (the audit view)
All 75 contacts with their gate outcome — `ADMIT` / `HOLD` / `REJECT` — the three signal results as
tick/cross, and the reason string. Filterable by conference and by decision.

This view is the answer to the first question a recruiter asks: *"what did it throw away, and why?"*
It also visibly demonstrates the signal-to-noise solution, which is the core of the brief.

### 5. Who can introduce us (reverse referral)
Grouped by **WSC employee**, not by candidate:

> **Maya Levi** — Senior ML Engineer, AI/ML
> Can introduce you to 4 candidates for Senior ML Engineer
> · Priya Anand — worked together at Mobileye (2019–21) — fit 90
> · Marcus Reid — 1st-degree connection — fit 83
> …
> [ Request intros ] *(mock — logs the Slack/email that would be sent)*

This is the differentiating screen. It turns the output from a list into an action, and it is the
one place the `work_history` column — undocumented in the brief — visibly pays off.

### 6. Integrations log
See `docs/09-mock-integrations.md`. A live log of the API calls the system *would* make against
HubSpot, Comeet and the enrichment provider. Turns "here's what production would look like" from a
paragraph in a document into a screen you can point at during the meeting.

## Persistent banner (required)

> **Synthetic data — recruitment exercise. No real candidate data.**

Plus `<meta name="robots" content="noindex, nofollow">`. The submission argues for Article 14
compliance; publishing realistic-looking candidate profiles unlabelled would undercut it.

## Out of scope for v1

No saved state, no "mark as contacted" persistence, no auth, no database. Those need a backend and
push past the effort the brief expects. The buttons that would write state are mocks that log — see
the next doc.
